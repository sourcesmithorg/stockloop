Decision ID: D-16 (preferences scope — a new ID beyond the register's D-01..D-15 range)
Status: proposed — implemented provisionally
Owner and source/date: unassigned — proposed by the M2 implementation agent, 2026-10-16; awaiting owner confirmation.
Question: Are display preferences per-user or per-store, how are they scoped, and how do concurrent edits behave?
Options considered:
1. Store-wide preferences (one row per store): simplest, but every member's locale/date-format choice would fight over one row; viewers could overwrite the owner's display settings.
2. Per-user preferences scoped to the store membership (chosen): each member owns their own `preference` row keyed by `(store_id, user_id)`; matches the honest "follow store" design where null means "inherit from store".
3. Global per-user preferences (no store dimension): survives a user belonging to two stores, but the data model gives each user exactly one active membership, and store-scoped keys keep isolation trivial.
Accepted policy (provisionally implemented, NOT accepted):
- `preference` is keyed by `(store_id, user_id)`; every row belongs to a real membership pair (FK to `store.id` and `user.id`). A user's preferences are always scoped to the store in their session — there is no cross-store leakage (asserted in `api/tests/test_session.py`).
- Fields (all nullable, camelCase): `locale`, `displayCurrency`, `timezone`, `dateFormat`, `numberFormat`, plus `version: int`. **Unknown/unsaved values stay `null` and are never coerced to a default** — null means "follow the store", per DATA-CONTRACTS.
- `POST /api/preferences` (self-scoped, no role gate beyond authentication): body `PreferencesUpdate` = any subset of the five fields plus `expectedVersion?`. Viewer/operator/owner may all edit their own row (D-04 matrix).
- Optimistic concurrency: if `expectedVersion` is supplied and != `preference.version`, respond 409 `{ "code": "version_conflict", "message": "Preferences were modified by another user", "currentVersion": <current> }`. On success, `version` increments only when a field actually changed and the response is `{ "preferences": <PreferencesOut incl. new version>, "version": <new> }`.
- A missing row is created lazily (version 1) on first write; `GET /api/store` and `GET /api/auth/me` return it as nulls until then.
- Preferences are display-only: changing them never mutates store data or historical documents; store-region changes do not relabel documents either.
Reason/tradeoff: scoping to `(store_id, user_id)` makes isolation a primary-key property instead of an access-check property, and null-means-inherit keeps the honest-unfilled contract (a coerced default would silently lie about what the user chose). Per-user rows mean membership revocation orphans the row — acceptable now, revisit when membership management lands (D-04).
Affected features / contracts / tests / tasks: `api/app/routers/preferences.py`, `api/app/schemas.py` (PreferencesOut/PreferencesUpdate/PreferencesResult), `api/app/services/auth.py` (`preferences_out`), `api/app/models.py` (`Preference`); tests `api/tests/test_preferences.py`, `api/tests/test_session.py`, `api/tests/test_authorization.py` (viewer may edit own prefs); frontend `pages/settings.tsx` save/conflict flow; Phase 4 E2E (stale `expectedVersion` → 409 with `currentVersion`).
Migration or compatibility impact: None — the `preference` table ships in the initial schema (alembic 0001) with `version` defaulting to 1.
External authorization needed: Owner must confirm (a) per-user versus store-wide scope, (b) that null-display preference remains "follow store" rather than a coerced default, and (c) whether `dateFormat`/`numberFormat` gain enumerated values or stay free-form.

Demo-mode isolation limitation (recorded 2026-10-16): the frontend demo mode exists and is labeled — the `VITE_USE_MOCK` build flag selects an in-memory fixture API, the header shows a "Demo data" pill, and layout chrome reads real session state with fixtures only under `USE_MOCK`. The backend has no equivalent: seed rows share the operational DB with real data, and provenance is limited to deterministic `uuid5` ids (fixed namespace in `api/app/seed.py::_id`) plus `source_version="fixture-v1"` markers on stock/sales rows — there is no queryable demo flag or separate dataset. Isolation beyond that would be a schema-level demo marker or a separate dataset and needs an owner decision; it is deliberately NOT implemented (proposal only, per this record's `proposed` status).
